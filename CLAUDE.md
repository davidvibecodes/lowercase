# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

lowercase is a gamified, peer-to-peer consulting case-prep app. Learners take adaptive concept quizzes, then run live Interviewer/Interviewee cases with a friend: revealable facts, "I'm Stuck" hints, a blue/grey issue tree, a transcript and a rubric. By default it runs **locally**: one machine, served on loopback, with SQLite. It can also run as a single public instance (Docker image, one persistent disk); that **hosted mode** switches on only when `PUBLIC_ORIGIN` is set. See `docs/hosting.md`. It is never scaled out: presence and invite timers are in memory.

Some directories have their own CLAUDE.md with the detail for that area: `src/lib/auth/`, `src/server/`, `src/app/`, `src/components/`, `prisma/` and `tests/`.

## Commands

| Command | What it does |
|---|---|
| `npm run dev` | Runs `ensure-db`, then `tsx watch server.ts` (Next.js + Socket.IO on http://localhost:3000) |
| `npm run build` | `prisma generate` + `next build` |
| `npm run start` | Runs `ensure-db`, then serves the production build (`NODE_ENV=production tsx server.ts`). It does **not** rebuild. |
| `npm run ensure-db` | Writes `.env` if missing, regenerates the Prisma client if the schema changed, backs up and migrates, and seeds an empty DB |
| `npm run typecheck` | `tsc --noEmit` (strict) |
| `npm run lint` | ESLint flat config (`next/core-web-vitals`, `next/typescript`) |
| `npm test` | Vitest unit and service suites against a freshly migrated `prisma/test.db` |
| `npm run test:e2e` | `npm run build`, then Playwright against an isolated server on port 3100 with a fresh `prisma/e2e.db` |

Running a subset:

```bash
npx vitest run tests/unit/social.test.ts
npx vitest run tests/unit/social.test.ts -t "reverse send"
npm run build && npx playwright test tests/e2e/friends.spec.ts
```

Playwright serves whatever is in `.next`. After a code change, run `npm run build` before a single spec, or it tests stale code.

**Dev reload boundaries.** `tsx watch` ignores `src/app`, `src/components` and `.next`. Edits there hot-reload through Next. Edits to `server.ts`, `src/server/**`, `src/lib/**` or `prisma/**` restart the whole process, so every socket drops and reconnects and in-memory state is lost: presence and pending invite timers.

**Windows.**
- Stop every Node process before `npm run build`, `npx prisma generate` or `npm run test:e2e`. A running dev, start, E2E or Vitest process holds the Prisma query engine, and `generate` fails with `EPERM`.
- The Prisma **binary** engine is used on purpose (`engineType = "binary"`), because the Node-API engine has no Windows ARM64 build.
- `.gitattributes` forces LF line endings.

**Resetting data.** Stop the server, delete `prisma/dev.db*`, then start it again; it reseeds. `ensure-db` seeds only when the `User` table is empty, so a change to the seed files never reaches an existing `dev.db`.

## Environment

`.env` is generated by `ensure-db`:
- `DATABASE_URL="file:./dev.db"`. Prisma resolves it relative to `prisma/`.
- a random `AUTH_SECRET`.
- `AUTH_MODE=dev`, which enables the passwordless test login.

Google sign-in needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `GOOGLE_REDIRECT_URI`, added by hand. See `.env.example` and the README's "Google sign-in" section. Until they are set, the login page explains what is missing and the test login still works. Nobody can be admin then, because only a Google session can be.

Hosted mode (`src/lib/hosting.ts`) is on exactly when `PUBLIC_ORIGIN` (e.g. `https://trylowercase.app`) is set, and it needs `AUTH_SECRET`, `DATABASE_URL`, the three `GOOGLE_*` values and a `GOOGLE_REDIRECT_URI` of `<origin>/login/google/callback`, or `server.ts` and `ensure-db` refuse to start (`hostedConfigProblems`). It changes these things, and only these:
- the Host/Origin allowlist pins to the public address instead of loopback (`src/server/loopback.ts`);
- the server listens on `0.0.0.0` (or `HOST`), and `GET /healthz` answers before the Host guard;
- session and sign-in cookies are `Secure` when the origin is https;
- the test login is off whatever `AUTH_MODE` says (`devLoginEnabled`);
- `ensure-db` never writes `.env`, seeds learning content only (`seedContent`: no people, no licensed Mumbai case), and keeps backups beside the database file;
- `src/server/backup.ts` writes a daily `VACUUM INTO` copy, newest 7 kept.

Test-only switches, never put in `.env`:
- `LC_FAKE_GOOGLE=1` plus a loopback `GOOGLE_OIDC_BASE_URL` points sign-in at the fake IdP in `tests/helpers/fake-google.ts`.
- `INVITE_TTL_MS` sets the session-invite expiry (default 120 s).
- `PORT` defaults to 3000.

There are three SQLite files: `dev.db` (the owner's real data), `test.db` (Vitest, recreated every run) and `e2e.db` (Playwright, recreated every run). Never point a test, script or migration-authoring command at `dev.db`.

## Architecture

### One process, two module graphs

`server.ts` is the entry point for dev and prod:
1. It loads `.env` via `@next/env`, because tsx doesn't.
2. It creates the Next app and an HTTP server bound to `127.0.0.1:PORT` (hosted: `0.0.0.0`).
3. It answers **421** to any Host other than `localhost:PORT` or `127.0.0.1:PORT` (when hosted: the public address only). This is a DNS-rebinding guard; see `src/server/loopback.ts`.
4. It attaches Socket.IO on the same port (`src/server/realtime/index.ts`), and hands every other WebSocket upgrade to Next for HMR.

`server.ts` (run by tsx) and the Next bundle load **separate copies** of shared modules. So anything both sides must see lives on `globalThis`:
- the Prisma client (`__lowercasePrisma`, `src/lib/db.ts`);
- the presence registry (`__lowercasePresence`, `src/server/realtime/presence.ts`);
- the live Socket.IO server (`__lowercaseIo`, `src/server/realtime/io-handle.ts`).

Server actions reach sockets only through `getIo()`. It returns `null` in processes without a socket server, such as unit tests, and callers treat that as a no-op. A new process-wide singleton must follow the same pattern.

### Layers

- `src/app`: routes. Pages are server components that call guards and services directly. Mutations go through `"use server"` actions in each route's `actions.ts`.
- `src/server/services`: all database logic. Functions take `db: Db` (or a transaction client) first, so tests can run them against `test.db`. User-facing failures throw `ServiceError`.
- `src/server/realtime`: Socket.IO handshake auth, presence, session-invite handlers, the live-session handlers and their broadcast queue.
- `src/lib`: code shared by server and client:
  - `types.ts`: domain constants and zod input schemas;
  - `rules/`: pure, unit-tested game rules (gates, streaks, XP, league, lesson selection, rubric, tree validation);
  - `realtime/events.ts`: the typed socket contract;
  - `auth/`;
  - `casebank.ts`: casebank parsing.
- `src/stores`: zustand client stores. `src/components`: UI.
- `prisma/`: the schema, migrations and seed content.

### How state moves

- **The database is authoritative; sockets carry events.** A live-session action is a socket emit with an ack. The handler validates the actor in `src/server/services/sessions.ts`, writes, acks, then `broadcastSession` sends each connected participant **its own** `SessionView`. Per session the queue builds one snapshot at a time, so a stale one never lands last.
- **Role projection is a security boundary.** The interviewee's view never contains unrevealed facts, unused hints, the tree, the transcript, recommendations, observations, casebook "given" facts, rubric data or any reveal-guidance field. Check `buildView` when adding anything to `SessionView`.
- **Page mutations use server actions, which return results rather than throwing.** Each `actions.ts` has a local `run()` wrapper that returns `{ ok: true, ...data } | { ok: false, error }`. A `ServiceError` message is shown to the user; anything else becomes "Something went wrong".
- **Socket handlers behave differently.** They return any `Error`'s message in the ack (`errorMessage` in `src/server/realtime/types.ts`), so a plain `throw new Error("…")` in a session service is user-visible text.
- Friend and group changes emit `social:changed` (the Received badge count) and `presence:update` from the action layer, **after** the transaction commits. See `src/server/realtime/social.ts`.

### Auth in one paragraph

The `lc_session` cookie is HMAC-signed with `AUTH_SECRET` and carries the user id plus how they signed in (`google` or `dev`). Admin is **computed**, never stored: `method === "google"` and email equals `ADMIN_EMAIL` (`davidsathyandevice@gmail.com`, a code constant). A user with a null `username` can reach only `/onboarding/username`. Every page, action, route handler and the socket handshake refuses them.

`src/middleware.ts` only checks that the cookie exists; real verification happens in `src/lib/auth/guards.ts`.

The test login (`AUTH_MODE=dev`) is limited to four seeded accounts, each only while it has never signed in with Google. It is never admin. Details: `src/lib/auth/CLAUDE.md`.

### Privacy rules for people

These are product requirements, not style. No screen lists users the viewer hasn't friended or searched for:
- People search matches an **exact** username only.
- League rows carry display name and XP, never a username.
- Group search shows the owner's display name, never a handle.
- A friend request is sent by username, never by user id, because league standings expose ids.

Queries that return people use `personSelect` plus the `onboarded` filter and map through `toPerson()` (`src/server/services/invites.ts`).

### Content model

- Concepts have explainer cards and questions.
- Cases have `CaseItem`s of kind `fact | hint | recommendation | observation | given`, transcript turns, and an issue tree stored as an adjacency list.
- Tree nodes have a **stable `key`**, unique per case, which survives the delete-and-recreate tree save. Facts and recommendations point at nodes by key (`nodeKey`, and `gatePrereqKeys` as a JSON array), never by row id.
- Items with session history are archived (`archivedAt`), never deleted. Live queries filter `archivedAt: null`.
- Casebank 2.0.0 JSON files are imported from Admin → Cases → Import (`src/lib/casebank.ts`, `src/server/services/casebank.ts`).

Status- and kind-like columns are plain SQLite strings. Their allowed values are the `as const` arrays in `src/lib/types.ts` (`SESSION_STATUSES`, `NODE_STATUSES`, `CASE_ITEM_KINDS`…), so add new values there.

## Conventions

- **Plan references in comments.** IDs like `R11`, `KTD8`, `U9` and `AE5` point into the plans under `docs/plans/`. There are two plans with **overlapping numbering**:
  - `2026-10-15-1309-feat-lowercase-case-prep-app-plan.md`: the original app. Its KTD1 is the custom server, KTD2 is DB-authoritative role projection, KTD4 is the peer-testing second hostname, KTD12 is the self-bootstrapping DB.
  - `2026-10-16-1510-feat-google-auth-friends-casebank-plan.md`: Google sign-in, onboarding, admin, sound, friends and casebank. Its KTD1–KTD16 and R1–R27 apply there.

  Tell them apart by topic. Before changing a behavior a comment cites, read that plan entry.
- `docs/reviews/2026-10-15-code-review-residuals.md` lists gaps left open on purpose:
  - a stateless cookie with no revocation;
  - `isCorrect` reaching the client;
  - a replayable lesson-XP action;
  - in-memory invite timers.

  Don't "fix" them incidentally.
- **Dependencies are pinned to exact versions.** `allowScripts` in `package.json` names the packages, with exact versions, allowed to run install scripts. Keep it in step when bumping Prisma or esbuild.
- Usernames are always normalized through `normalizeUsername()` (`src/lib/username.ts`): trimmed, leading `@` stripped, lowercased, `^[a-z][a-z0-9._]{2,19}$`. Emails are stored lowercase. Both columns' unique indexes rely on that.
- Text imported from a casebank is rendered as plain text. `components/ui/Markdown.tsx` is for authored concept and lesson content.

## Repository hygiene

- **The repo must stay private.** The "Diagnostic Center – Mumbai" seed case and transcript come from a licensed casebook. There is no git remote configured.
- These are gitignored and must never be committed or force-added:
  - `.env*` (except `.env.example`);
  - `prisma/*.db*` and `prisma/backups/`;
  - `content/private/`, where casebank JSON files are kept;
  - `UI/` and `*.docx`;
  - the `919322690407_s_whatsapp_net-*.jpg` reference images in the repo root, which are licensed casebook material.
- `.dockerignore` keeps the same files out of the image. Real production settings (`deploy/vm/production.env`) are never committed; only the `.example` is.
